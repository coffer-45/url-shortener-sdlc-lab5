# Вебсервіс скорочення URL — ЛР №5

Інтегрований навчальний моноліт Django (Python 3.10+, Django 5.2.18, SQLite).
Продовження ЛР №4 відповідно до архітектури ЛР №2. Окремих мікросервісів,
публічного API, SPA або QR-кодів немає: компоненти спілкуються внутрішніми викликами Python.

## Можливості

- FR-01/02: реєстрація, вхід і вихід через Django Auth;
- FR-03/04: створення HTTP/HTTPS-посилання з випадковим унікальним коротким кодом;
- FR-05/08: публічний перехід (302), 404 для невідомого коду, атомарний лічильник;
- FR-06/07: список і видалення **лише власних** посилань (POST + CSRF);
- FR-09: адміністрування користувачів і посилань у Django Admin.

## Структура та інтеграція

| Шлях | Призначення |
| --- | --- |
| `config/` | налаштування, URL-маршрути, WSGI |
| `links/models.py`, `links/migrations/` | `ShortLink` і схема SQLite |
| `links/forms.py` | реєстрація й перевірка URL |
| `links/services.py` | генератор, операції власника, перенаправлення і лічильник |
| `links/views.py`, `links/admin.py` | HTTP-представлення, авторизація, адмінпанель |
| `templates/links/` | HTML-сторінки браузера |
| `links/tests/` | модульні та наскрізні інтеграційні тести |
| `scripts/load_check.py` | локальна перевірка 20 одночасних HTTP-клієнтів |
| `docs/` | архітектура, матриця вимог, результати і обмеження |

Браузер → Django views → форми/сервіси → ORM → SQLite. Django Auth керує
паролями й сесіями; шаблони показують дані, не виконуючи SQL. Залежність
`Django==5.2.18` зафіксовано в `requirements.txt`; транзитивні залежності
встановлює pip. У моноліті лише один файл залежностей, конфліктів версій між
окремими компонентами немає.

## Локальний запуск

Потрібні Python 3.10+ із `venv`/`pip` і доступ до PyPI. З каталогу **`url_shortener/`**:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py runserver
```

Відкрийте `http://127.0.0.1:8000/register/`. Створіть акаунт, додайте посилання,
відкрийте коротку адресу й перевірте лічильник у списку. Адміністратора можна
створити через `.venv/bin/python manage.py createsuperuser`; `/admin/` доступний
лише персоналу. Локальний `runserver` **не** є сервером для production.

```sh
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test
```

Локальна перевірка продуктивності (після `migrate`, при запущеному `runserver`):

```sh
.venv/bin/python scripts/load_check.py --base http://127.0.0.1:8000
```

Скрипт створює 20 тимчасових акаунтів, відкриває `/links/`, `/links/new/` і
`/<code>/` у 20 одночасних сесіях (180 запитів за замовчуванням), вимірює
median/p95/max, видаляє тестові акаунти після виконання. **Тільки для локальної
тестової БД**, не для production. Статистика залежить від машини й сервера;
повторіть перевірку у своєму середовищі.

## Нефункціональні вимоги та межі перевірки

| Вимога | Реалізація / доказ |
| --- | --- |
| NFR-01 <2 с за 20 користувачів | Локальний прогін: 180 запитів, 0 помилок, max 0,903 с. Не гарантія для хостингу. |
| NFR-02 хешовані паролі | Django Auth, тест реєстрації та `check_password()` |
| NFR-03 лише HTTP/HTTPS | `LinkForm` і `LinkService`, негативні тести |
| NFR-04 Chrome/Firefox/Edge | Стандартні HTML-форми; повний ручний кросбраузерний прогін **не виконаний** |
| NFR-05 HTTPS | Параметри безпечних cookie й редиректу для production; потрібен реальний TLS-проксі, перевірка на хостингу **не виконана** |
| NFR-06 права доступу | Обмеження за власником, CSRF, staff-only Admin, наскрізний тест |
| NFR-07 збереження | Локальний файл SQLite, міграції; на хостингу потрібні постійний том і резервні копії; перезапуск хостингу **не перевірено** |

Повна матриця перевірок і чекліст ручного тестування: [`docs/integration.md`](docs/integration.md).

## Налаштування хостингу (не виконане розгортання)

- `DJANGO_DEBUG=0`, `DJANGO_SECRET_KEY=<довгий випадковий секрет>`,
  `DJANGO_ALLOWED_HOSTS=<домен>`, `DJANGO_DB_PATH=<файл на постійному диску>`;
  застосунок не стартує без секрету при `DJANGO_DEBUG=0`.
- Забезпечте TLS на довіреному зворотному проксі. Лише якщо проксі **видаляє**
  клієнтський `X-Forwarded-Proto` і сам задає його, встановіть
  `DJANGO_TRUST_PROXY_SSL=1`; без цього не довіряйте заголовку. Перевірте, що
  HTTP перенаправляється на HTTPS, а cookie мають прапорець Secure.
- Виконайте міграції, налаштуйте роздачу статики (`collectstatic` та вебсервер),
  резервне копіювання SQLite й надійний WSGI-сервер. Після налаштування запустіть
  `manage.py check --deploy` та усуньте попередження. HSTS вмикайте лише після
  перевірки стабільного HTTPS на всіх піддоменах.

## Зміни після ЛР №4

Скопійовано вихідний код без `.git`, локальної БД і кешів; версію Django
зафіксовано, додано наскрізні тести, локальну перевірку навантаження та
обмеження конфігурації production. Попередню ЛР №4 не змінено.
